Model Context Protocol

도구를 모델에 꽂는 규약 — 그리고 스스로를 덜어내는 중인 프로토콜

MCP를 "AI용 USB-C"라고 부르면 절반만 맞다. 규격을 통일했다는 점은 맞지만, 더 중요한 것은 무엇을 규정하지 않기로 했는가다. 최근 2026-07-28 개정판은 프로토콜에서 상태를 걷어내고, 클라이언트 프리미티브 넷 중 셋(sampling · roots · logging)을 폐기했다. 기능을 더한 개정이 아니라 범위를 다시 좁힌 개정이다.

01M×N 문제

모델에 외부 기능을 붙이는 일은 원래 제곱으로 늘어나는 통합 작업이었다. AI 애플리케이션이 M개, 연결할 시스템(깃허브, 파일시스템, 데이터베이스, 사내 API)이 N개면 필요한 커넥터는 M × N개다. 각 애플리케이션이 각 시스템마다 전용 통합을 따로 작성했다.

MCP는 이 사이에 규약을 하나 끼워 넣는다. 애플리케이션은 MCP를 한 번 말할 줄 알면 되고, 시스템은 MCP 서버를 한 번 만들면 된다. M × N이 M + N이 된다. 언어 서버 프로토콜(LSP)이 에디터와 언어 사이에서 한 일과 같은 구조다 — 실제로 MCP는 JSON-RPC 2.0을 쓴다는 점까지 LSP를 닮았다.

범위를 좁게 잡은 것이 설계의 핵심이다. MCP는 맥락을 주고받는 방법만 규정하고, 애플리케이션이 그 맥락으로 무엇을 하는지, 어떤 모델을 쓰는지, 프롬프트를 어떻게 구성하는지는 일절 규정하지 않는다. 공식 문서의 표현대로 "MCP는 오직 맥락 교환 프로토콜에만 집중한다." 이 절제 덕분에 특정 모델·특정 벤더에 묶이지 않는다.

02참여자 — 호스트, 클라이언트, 서버

용어가 혼동되기 쉬운데, 관계는 단순하다.

  • 호스트(Host) — AI 애플리케이션 본체. Claude Code, Claude Desktop, VS Code 같은 것. 여러 클라이언트를 만들고 관리한다.
  • 클라이언트(Client) — 서버 하나와의 연결을 유지하는 부품. 호스트 안에 산다.
  • 서버(Server) — 맥락을 제공하는 프로그램.

핵심은 클라이언트와 서버가 1:1이라는 것이다. 호스트가 서버 세 개에 붙으면 클라이언트 객체를 세 개 만든다. 하나의 클라이언트가 여러 서버를 관리하지 않는다. 이 격리 덕분에 서버 하나가 죽어도 나머지 연결은 살아 있고, 권한도 연결 단위로 끊을 수 있다.

03두 개의 층 — 데이터와 전송

MCP는 안쪽의 데이터 층과 바깥의 전송 층으로 나뉜다. 데이터 층은 JSON-RPC 2.0 기반의 메시지 의미를 정의하고, 전송 층은 그 메시지가 실제로 어떤 채널을 타고 오가는지를 정의한다. 둘이 분리돼 있어 같은 JSON-RPC 메시지가 어떤 전송에서도 그대로 통한다.

STDIO 전송

표준 입출력으로 같은 기계 안의 프로세스끼리 직접 통신한다. 네트워크 오버헤드가 없어 가장 빠르다. 로컬 서버의 기본 선택.

Streamable HTTP 전송

클라이언트→서버는 HTTP POST, 스트리밍이 필요하면 서버센트 이벤트(SSE)를 얹는다. 원격 서버용이며 표준 HTTP 인증(베어러 토큰 등)을 쓴다 — 권장은 OAuth.

과거의 HTTP+SSE 전송은 폐기됐다(2025-03-26 기준). 새로 만든다면 Streamable HTTP를 쓴다.

04프로토콜이 상태를 버렸다

여기가 최근 개정에서 가장 크게 바뀐 지점이다. 초기 MCP는 연결을 맺고 핸드셰이크를 한 뒤 그 상태를 유지하는 구조였다. initialize로 버전과 능력을 합의하고, 이후 요청들은 그 합의를 전제로 오갔다.

2026-07-28 개정판의 MCP는 상태 없는(stateless) 프로토콜이다. 모든 요청이 스스로를 처리하는 데 필요한 정보를 전부 담는다. 프로토콜 버전과 클라이언트 능력이 매 요청의 _meta 필드에 실린다. 서버는 이전 요청을 기억할 필요가 없다.

매 요청에 실리는 _meta
"_meta": {
  "io.modelcontextprotocol/protocolVersion": "2026-07-28",
  "io.modelcontextprotocol/clientInfo": { "name": ..., "version": ... },
  "io.modelcontextprotocol/clientCapabilities": { "elicitation": {} }
}

능력 탐색은 server/discover 요청 하나로 대체됐다. 모든 서버가 반드시 구현해야 하고, 응답은 지원 버전 목록과 능력, 그리고 캐시 힌트(ttlMs, cacheScope)를 담는다. 게다가 선택 사항이다 — 어차피 모든 요청이 버전을 들고 다니므로, 클라이언트는 곧바로 원하는 요청을 보내고 버전 오류가 오면 그때 맞춰도 된다.

왜 상태를 버렸나. 상태 있는 연결은 원격 서버에서 비싸다 — 로드 밸런서 뒤의 어느 인스턴스가 그 세션을 들고 있는지 관리해야 하고, 재연결마다 핸드셰이크를 다시 해야 한다. 상태가 없으면 아무 인스턴스나 아무 요청이나 처리할 수 있다. HTTP가 상태를 버려서 웹이 확장된 것과 같은 이유다. 대가는 매 요청의 메타데이터 오버헤드인데, 캐시 가능한 server/discover가 그것을 상당 부분 상쇄한다.

05프리미티브 — 그리고 사라지고 있는 것들

프리미티브는 서로에게 무엇을 제공할 수 있는가를 규정한다. 서버 쪽 셋이 핵심이다.

서버 프리미티브무엇인가주요 메서드제어 주체
Tools실행 가능한 함수 — 행동을 수행tools/list · tools/call모델이 호출
Resources맥락 데이터 — 파일 내용, DB 레코드resources/list · resources/read애플리케이션이 선택
Prompts재사용 가능한 상호작용 템플릿prompts/list · prompts/get사용자가 호출

패턴이 일정하다. 발견은 */list, 사용은 */get 또는 tools/call. 목록이 런타임에 결정되므로 서버가 상황에 따라 도구를 늘리거나 줄일 수 있다.

클라이언트도 프리미티브를 제공한다 — 서버가 거꾸로 요청을 걸 수 있게 하는 장치다. 그런데 여기가 최근 크게 정리됐다. 2026-07-28 기준으로 살아 있는 클라이언트 프리미티브는 하나뿐이다.

  • Elicitation (유효). 서버가 사용자에게 추가 정보를 요청한다. 확인을 받거나 빠진 값을 물을 때 쓴다. elicitation/create.
  • Sampling (폐기). 서버가 클라이언트에게 모델 추론을 요청하던 기능. 서버가 LLM SDK를 품지 않고도 모델을 쓸 수 있게 하려던 것이었으나, 이제 LLM 제공자 API에 직접 통합하라는 권고로 대체됐다.
  • Roots (폐기). 클라이언트가 서버에 파일시스템 경계를 알려 주던 기능. 도구 파라미터나 리소스 URI, 서버 설정으로 넘기는 방식으로 대체됐다.
  • Logging (폐기). 서버가 클라이언트로 로그를 보내던 기능. STDIO에서는 stderr로, 관측이 필요하면 OpenTelemetry로 대체됐다.
폐기는 즉시 제거가 아니다. MCP는 기능 수명주기 정책을 두고 있다. 폐기된 기능은 명세에 남아 있되 새 구현은 채택하지 말아야 하고, 실제 제거는 2027-07-28 이후 릴리스부터 가능해진다. 지금 MCP 서버를 새로 만든다면 sampling·roots·logging에 의존하지 않는 편이 안전하다.

이 정리의 방향은 분명하다. MCP를 다시 좁히는 것이다. sampling은 프로토콜이 모델 추론까지 중개하게 만들었고, roots는 파일시스템 개념을 프로토콜에 새겼고, logging은 관측 도구가 이미 잘하는 일을 중복했다. 세 가지 모두 "맥락 교환"이라는 원래 범위를 넘어선 것이었다.

06알림은 이제 구독해야 받는다

서버의 도구 목록이 바뀌었을 때 클라이언트에 알리는 메커니즘도 상태 없는 설계에 맞춰 바뀌었다. 과거에는 연결만 있으면 알림이 흘러왔지만, 지금은 명시적으로 구독해야 한다.

구독 → 확인 → 알림
→ subscriptions/listen { notifications: { toolsListChanged: true } }
← notifications/subscriptions/acknowledged (서버가 수락한 항목만 반영)
← notifications/tools/list_changed (변경 발생 시)

확인 응답이 중요하다. 서버는 자신이 지원하는 알림만 골라 수락하고 나머지는 응답에서 빠뜨린다. 클라이언트는 무엇을 실제로 받게 될지 확실히 알 수 있다. 모든 알림에는 구독 요청의 JSON-RPC ID가 subscriptionId로 붙어 어느 구독에서 온 것인지 추적된다.

다만 명세는 알림이 최선 노력(best effort)이라고 못 박는다. 특히 전송 재연결 구간에서 알림이 유실될 수 있으므로, 클라이언트는 폴링도 병행해 신선도를 유지해야 한다. 알림을 유일한 진실 공급원으로 삼는 설계는 위험하다.

07실무에서 걸리는 지점들

  • 도구 이름은 네임스페이스처럼. 여러 서버의 도구가 한 모델의 도구 목록에 합쳐지므로 calculate보다 calculator_arithmetic이 낫다. 충돌이 실제로 일어난다.
  • 도구 설명은 트리거 조건까지 쓴다. 모델은 설명을 읽고 언제 부를지 정한다. "무엇을 하는가"만이 아니라 "언제 불러야 하는가"를 명시하면 호출률이 눈에 띄게 오른다.
  • 도구가 많으면 점진적 발견을 쓴다. 서버를 여럿 연결하면 도구 수가 금방 수십 개가 된다. 전부 미리 올리는 대신 필요할 때 찾아 올리는 방식이 문맥과 정확도 양쪽에 유리하다.
  • 캐시 힌트를 존중한다. ttlMs와 cacheScope가 응답에 실린다. 매 요청마다 tools/list를 다시 부르는 클라이언트는 상태 없는 설계의 비용만 지불하고 이득은 못 챙긴다.
  • 원격 서버는 인증이 본체다. Streamable HTTP는 표준 HTTP 인증을 쓰고 OAuth를 권장한다. 참고로 동적 클라이언트 등록(DCR)도 폐기 대상이 되어 Client ID Metadata Documents로 옮겨 가고 있다.

한 걸음 물러나 보면, MCP의 최근 개정은 프로토콜이 스스로를 덜어내는 과정이다. 상태를 버려 확장성을 얻고, 모델 추론·파일 경계·로깅을 밖으로 밀어내 범위를 좁혔다. 좋은 프로토콜은 기능을 더해서가 아니라 무엇을 규정하지 않을지 정확히 알아서 오래간다. TCP가 그랬고 HTTP가 그랬다. MCP가 지금 그 방향으로 스스로를 다듬고 있다.
